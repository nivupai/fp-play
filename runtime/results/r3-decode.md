# R3: does sharding change the tokens?

Generated by `fp-play-runtime experiment --out results`. Every number below comes from that run.

## Setup

- Model: a Llama-style decoder (RMSNorm, RoPE, grouped-query attention, SwiGLU, tied embeddings) with deterministic random BF16 weights (checksum `a77eb64e8be2d81b`): hidden 256, 2 layers, 16 query and 8 KV heads of dimension 16, FFN 704, vocabulary 2048, 2000128 parameters.
- Arithmetic: local kernels (matrix–vector products, RMSNorm, attention, softmax, SwiGLU, residual adds) use binary32 basic operations in one written order, with `exp`, `sin` and `cos` built from binary64 basic operations. Weights and the KV cache are BF16; the residual stream, attention and logits are binary32. Each row-parallel projection (attention output, MLP down; two per layer) produces binary32 partials that go through the executed AllReduce under the wire policy, whose BF16 output is added to the residual stream. Under the shard tree each of S = 64 shards sums its slice of the input dimension in a fixed order; the tree depends only on S.
- Workload: 32 prompts of 16 tokens (4 groups sharing a 8-token prefix), 48 greedy tokens each, one sample, no end-of-sequence token. Served through the R2 engine (block size 4); every scheduler, token-stream, KV-cache and tensor invariant is checked after every step.
- Baseline: P = 1 with the same wire policy and logit scale. P = 1 runs no collective: each projection's binary32 sum is rounded once to BF16. The shard tree at P = 1 still combines its 64 shard partials, so it differs from the baseline by a fixed change of arithmetic.
- Divergence: a prompt diverges at the first generated token that differs from the baseline. Its context matches the baseline up to and including that token, so every token up to it is *at risk*: there the baseline's top-2 margin and the run's logit perturbation (the largest |run − baseline| over the vocabulary) are comparable. Margins and perturbations are given in ulps of the baseline's top logit (binary32).

## 3. Batch invariance (P = 4, and a P = 1 control)

Each prompt's logits in each batch composition, compared bit for bit with the same prompt served alone. Each cell: prompts whose logits differ / prompts whose tokens differ (of 32).

Prediction, derived from the schedules before measuring: local arithmetic is per token, so only a reduction whose expression for an element depends on the element's index in the step buffer can make the bits depend on the batch. Sequential and binomial-tree reduce every element alike, exact-gather sums each element exactly, the shard tree's tree depends only on S, and halving-doubling at a power-of-two P combines (x0 + x2) + (x1 + x3), up to commutativity, for every element. The ring folds each chunk starting from a different rank. So only the ring should vary.

- **together**: all prompts arrive at once; budget 1024 tokens, so every prefill runs in one step.
- **reversed arrival**: as together, arrival order reversed.
- **chunk 8**: budget 8 tokens: 8-token prefill chunks, at most 8 tokens per step.
- **chunk 64**: budget 64 tokens.
- **prefix cache**: budget 64 with prefix caching: shared-prefix K/V reused from earlier steps.
- **recompute preemption**: as together with 5/8 of the KV blocks the workload needs: recompute preemptions.
- **failure + retry**: as together; a rank fails a quarter of the way through decoding (last layer, MLP AllReduce); retry recomputes.

## 4. What determinism costs

Latency is not recomputed here. R2 measured the deterministic pairing (shard tree with `fp32-rs/bf16-ag`) against ring on the 8B-class serving model: see `results/r2-serving.md`, section 4, "The deterministic pairing". This experiment adds what that pairing buys in tokens: its rows above are the same at every P (section 1) and in every batch composition (section 3).

## What this does and does not show

- It shows, with every rounding executed, where a tensor-parallel decoder's tokens can change: with P and the schedule through the row-parallel AllReduces, and with batch composition only through a schedule whose reduction order depends on an element's place in the step buffer.
- The weights are random. Margins in a trained model are distributed differently, so the divergence rates here do not transfer to trained models. Greedy decoding with these weights often repeats a token for many steps.
- The model is tiny (2 layers, hidden 256) and the prompts are synthetic.
- Local kernels are sequential and batch-invariant by construction. Real GPU kernels choose tilings and split-K reductions by batch shape, which can break batch invariance locally as well; that is not modeled.
- Greedy decoding only, fixed output lengths, no sampling. `exp`, `sin` and `cos` are deterministic but not correctly rounded.
- No latency is measured or modeled here; the cost of determinism is R2's illustrative serving model.
