# R1.1: BF16 output with FP32 where it can help

Generated by `fp-play-runtime experiment --out results` (fp-play-runtime 0.1.0). Re-running the command reproduces this file byte for byte.

**Setup.** The problem of [tp-allreduce.md](tp-allreduce.md): `Y = X·W`, X 8×4096 and W 4096×512 in BF16 (seed `0xf991a7`), the hidden dimension split across P devices, each computing an FP32 partial over its slice (exact products, one FP32 rounding per term). The output is BF16. 4096 output elements per run. All arithmetic is exact with one round-to-nearest-even per modeled operation.

**Policies.** These are modeled policies, not descriptions of any particular library.

- `bf16` — R1's BF16 wire: every FP32 partial is rounded to BF16 before the collective, and every combine is a BF16 addition. 2 bytes per element in every phase.
- `fp32-rs/bf16-ag` — FP32 partials and FP32 additions. Reduce phases (reduce-scatter, chain or tree reduce, exact-gather's input gather) send FP32, 4 bytes per element; a finished value is rounded once to BF16, and gather phases (all-gather, broadcast) send BF16.
- `bf16-wire/fp32-add` — FP32 partials and FP32 additions, but every message is BF16: each hop rounds the sender's FP32 partial to BF16 and the receiver adds it to its own FP32 partial. 2 bytes per element in every phase.

**References.** **≠ exact** — elements differing from the exact dot product rounded once to BF16. **≠ ideal** — elements differing from the exact sum of the P FP32 partials rounded once to BF16: the best any collective can do once the local kernels have run. The unsharded FP32 kernel rounded to BF16 differs from exact on 0.05% of elements.

Columns: **roundings/elem** — operations that can round in each output element's reduction tree, before the collective (the conversion of the P partials) + inside it (measured from the schedule; additions, roundings of an exact sum, and narrowing conversions); **rel. RMS err** — ‖Y − Y_exact‖₂ / ‖Y_exact‖₂ in binary64 (a display estimate); **top-1 Δ** — tokens whose argmax output changes vs the unsharded kernel; **reduce / gather B/rank** — the most bytes any rank sends in reduce phases and in gather phases; **est. µs** — α–β estimate (α = 2 µs, 100 GB/s per link; illustrative, not a measurement).

## What this does and does not show

- The two mixed policies are modeled from their definitions above; neither is attributed to any library or hardware.
- **≠ ideal** isolates the collective: the ideal already includes every rounding of the local FP32 kernels, so the gap from ideal to exact is the kernels', not the collective's. Exact-gather under `fp32-rs/bf16-ag` sums the FP32 partials exactly and rounds once, so it is the ideal by construction.
- `bf16-wire/fp32-add` performs as many roundings per element as `bf16` (one per partial plus the additions); the difference is where they happen. In the reduction schedules additions are FP32 and the receiving device's own partial is never quantized. Exact-gather uses every input in its wire form, the device's own included, so under this policy it gives exactly the `bf16` exact-gather output.
- Reduce-scatter chunks are ranges of the flattened, token-major output. They line up with token boundaries only when P divides the token count, so this is not exactly a sequence-parallel layout for every P.
- Inputs are synthetic (Irwin–Hall normal, weights scaled by 1/√hidden); the local kernel is one sequential order, not a blocked GEMM; the cost model ignores contention, compute and overlap. No hardware or interconnect measurement is claimed.
